API: a predecessor task accepts several bound successor chains

Several chains can be bound with afterTaskId to the same predecessor task, so a wave that fans out from one delivered chain no longer has to be serialised.

Background: Task.dispatchAfterTaskId in packages/db/prisma/schema.prisma carries `@unique` and a composite `@@unique([dispatchAfterTaskId, projectId])`, and instantiate (packages/api/src/templates.ts, the "occupied" check near line 650 and the unique-violation classifier near line 318) refuses a second binding with `after_task_already_bound`. Activation of a bound chain is pull-based: the bound first step is startable when its `dispatchAfter` predecessor is DONE (packages/api/src/chain.ts, predecessorsDone / bindingResolved), the board reads predecessors through a map keyed by dispatchAfterTaskId (packages/api/src/board.ts), and the barrier and activation tests (chain-activation-barrier.dbtest.ts, dispatch-activation.dbtest.ts, template-dispatch-binding.dbtest.ts) exercise one successor. Nothing in the completion path pushes to a single successor, so the one-to-one rule is enforced only by the index and the instantiate refusal. On 2026-09-06 a four-chain wave whose chains B and C both depended on chain A had to be serialised A → C → D → B solely because of this rule. docs/operator-api.md (instantiate and start routes) and docs/governance/task-routing-v1.md ("each predecessor task accepts one successor") state the rule.

Changes:
1. A Prisma migration drops both unique constraints on Task.dispatchAfterTaskId and replaces them with a non-unique index on `[dispatchAfterTaskId, projectId]`; the schema matches. The migration does not change RELEASE_CANDIDATE_MIGRATIONS.
2. Instantiate no longer refuses a second binding to the same predecessor: the `after_task_already_bound` refusal, the unique-violation classifier branch that mapped the index error to it, and their tests are removed. Every other afterTaskId refusal (not found, archived, predecessor not a chain task, autoStart conflict, one-hop depth) is unchanged.
3. The predecessor's activity entry "Chain <id> bound to predecessor <name>" is still written once per binding, so a predecessor with three successors has three entries.
4. `DELETE /tasks/:taskId/chain` on one successor releases only that successor's binding; the others stay bound. The board's blocked-on projection shows each bound successor blocked on the same predecessor.
5. When the predecessor becomes DONE every bound successor's first step becomes startable under the existing activation barrier, and a manual start of any one of them does not affect the others.
6. docs/operator-api.md (instantiate, start, and chain delete routes) and docs/governance/task-routing-v1.md replace the one-successor statement with the several-successors rule; the routing doc's dependency-qualification text keeps `afterTaskId` binding one-way and one hop deep.

Out of scope: fan-in (several predecessors for one chain, ruled out 2026-08-31); changing activation timing, the activation barrier, or hold/resume semantics; automatic starting of successors beyond what exists today; the web client beyond what the existing blocked-on rendering already shows; any other schema change.

Constraints: the binding remains one-way and one hop; a successor still refuses manual start until its predecessor is DONE. Refusal codes that remain keep their names and messages. The migration must apply on a database that already holds at most one successor per predecessor without data changes.

Acceptance: migration applies and `npx prisma migrate diff` reports no drift; a database-backed test binds two chains to one predecessor and proves both instantiations succeed, both first steps are refused manual start while the predecessor is TODO, both become startable after it is DONE, and deleting one successor's chain leaves the other bound; a test proves the predecessor carries one binding activity per successor; the board projection test proves two successors report blockedOn the same predecessor; the removed refusal has no remaining reference in packages/api or docs; `npm run lint`, `npm run typecheck`, `npm run test -w @anneal/api` and `npm run test -w @anneal/db` are green; docs/operator-api.md and docs/governance/task-routing-v1.md state the several-successors rule.
