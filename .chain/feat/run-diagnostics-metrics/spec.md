Web: Task detail shows per-run diagnostics (phases, token split, tool stats, effective output rate)

Every run on the task detail page exposes where its wall clock went, how its tokens split, how its tools behaved, its effective output rate and how it terminated, computed server-side from data the platform already stores.

Background: GET /tasks/:taskId (packages/api/src/routes/tasks.ts, the route at ~line 302) returns every run with its full Session row. Session already stores inputTokens, cachedInputTokens, cacheCreationInputTokens, outputTokens, costUsd, provisionedAt, startedAt, endedAt, cleanupStartedAt, cleanupEndedAt, terminationReason, exitCode and signal; Run stores readyAt and lastProgressEventAt. SessionEvent rows (columns type, at, toolCallId, payload, seq) are emitted by the runner adapters in packages/runner/src/adapters/{claude,codex,pi}.ts through emitAdapterEvent in adapters/runtime.ts with types MODEL_STARTED, MODEL_DELTA, MODEL_COMPLETED, TOOL_STARTED, TOOL_PROGRESS, TOOL_COMPLETED, ADAPTER_ERROR, FINAL_OUTPUT, PROVIDER_STATUS, PROVIDER_RAW. Tool events carry toolCallId so a start can be paired with its completion. packages/api/src/costs.ts (~lines 267-290) owns the canonical input-token split rule (cached reads and cache writes are subsets of inputTokens; an inconsistent split is treated as unknown). The web page apps/web/src/pages/TaskDetail.tsx shows only duration (durationWithInboxWait), totalTokens and spend per run; token split, cache ratio, phase breakdown, tool behaviour and termination are invisible, so an operator cannot tell whether a slow run was slow in the model, in tools, in provisioning or waiting for the inbox.

Changes:
1. A new pure module packages/api/src/run-metrics.ts computes a `metrics` object from a Run, its Session and that session's TOOL_STARTED/TOOL_COMPLETED SessionEvent rows. It has no database access of its own and is unit-tested with fixtures.
2. `metrics.phases` carries millisecond durations: `queuedMs` (Run.readyAt to Session.provisionedAt), `provisioningMs` (provisionedAt to startedAt), `executingMs` (startedAt to endedAt, or to now while the run is live), `inboxWaitMs` (the time the session spent waiting on inbox replies, derived from the same data the existing "includes inbox wait" label in TaskDetail is derived from; null when that data cannot bound it), `cleanupMs` (cleanupStartedAt to cleanupEndedAt). Each value is null when either bounding timestamp is missing; null is never rendered as 0.
3. `metrics.tokens` carries `input`, `cachedRead`, `cacheWrite`, `uncachedInput`, `output` and `cacheHitRatio` (cachedRead / input) using the costs.ts split rule, exported from costs.ts rather than duplicated; `cacheHitRatio` and `uncachedInput` are null when the split is invalid or any component is null.
4. `metrics.tools` carries `calls`, `failed`, `unclassified`, `totalToolMs` and `byName` (top five tool names by call count, each with calls and failed). Pairing is by toolCallId. Failure is decided per runner from the persisted TOOL_COMPLETED payload: Claude `tool_result` with `is_error === true`; Codex `command_execution` items with a non-zero exit code or an item-level `error`; PI `tool_execution_end` with its error marker. The implementer verifies the exact field names against the adapter fixtures under packages/runner/src/adapters and records them in the module's comments. A completion whose payload cannot be classified counts in `unclassified`, never silently as success. An unpaired TOOL_STARTED counts as a call with unknown duration.
5. `metrics.modelActiveMs` = executingMs − totalToolMs − inboxWaitMs (null inputs treated as 0 only for the subtraction and flagged by `metrics.modelActiveIsUpperBound: true`; clamped at 0). `metrics.outputTokensPerSecond` = output / (modelActiveMs / 1000), null when output is null or modelActiveMs is null or 0. The operator handbook and the UI label it as an effective session-average rate, not a provider peak rate.
6. `metrics.termination` carries `reason` (Session.terminationReason), `exitCode` and `signal`.
7. GET /tasks/:taskId attaches `metrics` to every entry of `runs[]`. The tool events for all of the task's runs are loaded in one query selecting only id, sessionId, type, at, toolCallId and payload, filtered to the TOOL_STARTED and TOOL_COMPLETED types; MODEL_DELTA and PROVIDER_RAW payloads are never loaded for metrics.
8. apps/web/src/pages/TaskDetail.tsx renders, per run, an expandable diagnostics block: a labelled phase bar (queued / provisioning / executing / inbox wait / cleanup), a token row (input, cached read, cache write, output, cache hit %), a tools row (calls, failed, unclassified, top tools), effective output rate, and termination. The existing tokens stat pill additionally shows the cache hit % of the latest run when known. All strings go through i18n in apps/web/src/locales/en.ts and zh.ts.
9. apps/web/src/lib/types.ts and the API response contract types carry the `metrics` shape.
10. docs/operator-api.md, section GET `/tasks/:taskId`, documents `metrics` field by field, including the null semantics and the effective-rate definition.

Out of scope: board cards and chain aggregate cards; time-to-first-token (a later chain adds it); per-template baselines and comparisons; the Costs page and costs.ts aggregation semantics; any change under packages/runner (no new SessionEvent types, no new payload fields); the Sessions page; database schema or migrations; changing how durationWithInboxWait is computed.

Constraints: metrics are derived at read time and never persisted. null always means unknown. No payload field is assumed to exist: an unexpected shape produces `unclassified` or null, never a thrown route error and never a silent success count. The route's query count for a task must not grow with the number of runs (one events query per task, not per run).

Acceptance: run-metrics unit tests cover, per runner, a fixture with one successful and one failed tool call proving calls, failed, totalToolMs and byName; a fixture with an unclassifiable completion proving `unclassified`; phase fixtures with each bounding timestamp missing proving null; a live run proving executingMs is measured to now; token fixtures proving cacheHitRatio and uncachedInput, including an invalid split yielding null; outputTokensPerSecond null when modelActiveMs is 0. A route test asserts every `runs[]` entry of GET /tasks/:taskId carries `metrics` and that the events query is issued once per request. Web tests render the diagnostics block with null fields shown as unknown, not 0. `npm run lint`, `npm run typecheck`, `npm run test -w @anneal/api` and `npm run test -w @anneal/web` are green. docs/operator-api.md documents `metrics`.
