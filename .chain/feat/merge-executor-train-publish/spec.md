Merge executor: a train-prefix authorization is published as a fast-forward and its candidate PRs read as merged

Goal: the merge executor can publish a control-plane-authorized cumulative merge prefix in one write under the GitHub App identity, and its replay classification recognises a pull request that was merged by that publication instead of stopping with `changed-underneath-me`.

Background: `packages/merge-executor/src/decision-table.ts` `execute` re-verifies the exact-head authorization (`authorization.headSha`, `baseSha`, `mergeMethod === AUTHORIZED_MERGE_METHOD`) against the live pull request and merges through the GitHub merge API in `github.ts` (`deps.merge(reference, expectedHeadSha, expectedBase)` via `confirmedWrite`). `classifyMerged` accepts a merged pull request only when `headRefOid === authorization.headSha`, `mergedByLogin` is the executor identity, a prior intent exists and the merge commit's two parents are exactly `(authorization.baseSha, authorization.headSha)`; anything else stops as `changed-underneath-me` or `base-drift-post-merge`. A merge train (ADR-0002; runtime tool from the chain "Merge train: a runtime tool builds, gates and records cumulative prefixes") produces a prefix commit `P_k = merge(P_{k-1}, C_k)` reachable at `refs/anneal/train/<prefixOid>`, where `P_0` is the authorized base. Publishing `P_n` as the new `main` merges candidates `C_1..C_n` at once; GitHub then reports each candidate pull request as merged with merge commit `P_k` whose parents are `(P_{k-1}, C_k)`, and `mergedBy` is whoever moved the ref. Today the executor has no way to publish such a prefix and would reject the resulting pull-request state on replay.

Changes:
1. The `merge-authorization` step output gains an optional `train` object: `{"publishHead":"<prefix oid, 40>","predecessorOid":"<40>","ref":"refs/anneal/train/<publishHead>","position":<1-based index of this candidate in the prefix>,"trainTaskId":"<id>"}`. Its parser in `packages/db` (next to the existing authorization schema) rejects a `train` whose `publishHead` or `predecessorOid` is not a 40-hex sha, whose `ref` does not equal `refs/anneal/train/<publishHead>`, or whose `position` is not a positive integer. An authorization without `train` is unchanged in shape and meaning.
2. When the claimed authorization carries `train`, `execute` verifies before any write that: the live pull request head equals `authorization.headSha`; the ref `refs/anneal/train/<publishHead>` exists on the repository and resolves to `publishHead`; `publishHead` contains `authorization.headSha` as an ancestor; and the live default branch head equals `authorization.baseSha` when `position === 1`, or is an ancestor of `publishHead` otherwise. Any mismatch stops with a new named outcome `train-precondition-failed` carrying the failing check, records it like the other stops, and performs no write.
3. Publication of a train authorization updates `refs/heads/<default branch>` to `publishHead` through the GitHub git-refs API as a non-forced update under the App installation token (a fast-forward; a non-fast-forward response is a stop `train-publish-rejected`), using the same `confirmedWrite` read-back discipline and idempotency key mechanism the merge API path uses. If the default branch already equals `publishHead` or contains it, the write is skipped and the outcome continues to Change 4.
4. After publication, or on replay, the executor reads the candidate pull request and reports the run as `merged` when the pull request is merged, `mergeCommitSha` is `P_k` for this candidate's position (the commit reachable from `publishHead` whose second parent is `authorization.headSha`), and that commit's parents are exactly `(predecessor, authorization.headSha)` where the predecessor is `authorization.baseSha` for position 1 or the previous prefix commit otherwise. `mergedByLogin` is not required to be the executor identity for a train publication, because GitHub attributes a ref update differently from an API merge; the lineage check replaces that guard. A pull request merged by any other shape still stops as `changed-underneath-me`.
5. The `GUARDED_MERGE_SENDS` resend bound and the `superseded-authorization` recheck apply to the ref update exactly as they apply to the merge call.
6. The train ref `refs/anneal/train/<publishHead>` is deleted after the candidate at the highest position in that prefix reports `merged`; deletion failure is logged, never a stop.
7. Documentation: `docs/runbooks/merge-executor.md` gains a section on train publication and its two new stop outcomes; `docs/operator-api.md`'s authorization output description names the optional `train` object.

Out of scope: producing the `train` authorization (the control plane), candidate selection, the runtime tool that builds prefixes, the merge lease, `scripts/merge-train.mjs`, canonical templates, any change to single-candidate authorization behaviour, GitHub App installation or credential handling, and the executor daemon lifecycle (startup preconditions, contract version, parking) that the in-flight executor chains own.

Constraints: an authorization without `train` behaves byte-for-byte as before and its existing tests pass unchanged; every new stop is a named outcome recorded through the same completion path as the existing stops; no write happens before every Change 2 check passes; the ref update is never forced; secrets handling and redaction stay as they are.

Acceptance: `packages/merge-executor` unit tests cover: train authorization parsed and rejected per Change 1; Change 2 preconditions each failing individually with `train-precondition-failed`; a successful fast-forward publication followed by `merged` for positions 1 and 2 of a two-candidate prefix; replay after the ref already moved reporting `merged` without a second write; a non-fast-forward response reporting `train-publish-rejected`; a merged pull request with a wrong second parent still stopping as `changed-underneath-me`; ref cleanup after the last position. `npm run test -w @anneal/merge-executor` and `packages/db` tests pass; existing `decision-table.test.ts` cases pass unchanged; `npm run lint` is clean; both documents in Change 7 are updated in the same diff.

Change 8 (added 2026-09-06 from the OSS-compare audit finding C-13, before this chain resumed): for a train authorization the pre-merge base check and the merged-commit parent check accept the prefix, not only the authorized base. `classifyPreMerge` today requires `snapshot.baseRefOid === authorization.baseSha` (`packages/merge-executor/src/decision-table.ts`) and `hasAuthorizedParents` requires `commit.parents[0] === authorization.baseSha`; for the candidate at position k > 1 the live base has already advanced to `P_{k-1}` by the time it executes, so both would stop it as `base-drift`. When the claimed authorization carries `train`, a live base that is not `authorization.baseSha` is accepted exactly when it is a commit of this prefix — reachable from `publishHead` and equal to `P_{k-1}` for this candidate's position; anything else stays `base-drift` unchanged. The merged-commit parent check reads against that same `P_{k-1}` rather than `authorization.baseSha`. Mergify's `Train.is_synced_with_the_base_branch` (`merge_train.py`) is the reference shape: it does not require the base to be unchanged, it requires the new base to be exactly the commit the train just published. An authorization without `train` keeps the strict equality byte-for-byte.

Acceptance (added with Change 8): unit tests cover a two-candidate prefix in which position 2 executes with the live base already at `P_1` and is published rather than stopped; a train candidate whose live base is an unrelated commit still stopping as `base-drift`; a train candidate whose live base is a prefix commit of a different `publishHead` still stopping as `base-drift`; and the merged-commit parent check passing against `P_1` for position 2. A non-train authorization whose live base moved still stops as `base-drift`, with its existing test unchanged.
