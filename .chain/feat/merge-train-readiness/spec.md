Merge readiness: ready chains publish through a merge train when a width is set, replacing per-chain drift re-runs

Goal: when the merge train is enabled, chains whose Regression evidence is valid are authorized together as the longest passing cumulative prefix from one train run under one merge lease, so a base move costs one shared train instead of one full Regression run per chain.

Background: `packages/api/src/merge-readiness-worker.ts` handles one chain at a time: `readReadiness` validates the Regression `regression-verification-v2` PASS bound to `(headSha, baseHeadSha)`, `runReadinessDecision` acquires the merge lease through `withMergeLease` (ADR-0003), `evaluateReadiness` in `readiness-decision.ts` re-reads the pull request and, when the base advanced, returns `requeue-regression`, which `requeueRegressionSettlement` turns into "Automatic base-drift recovery": the chain's Regression task is reset and re-run (full gate plus semantic verification) against the new base, bounded by `MAX_AUTOMATIC_BASE_DRIFT_RECOVERIES`. With 17 to 26 chains in flight every publication invalidates every other chain's PASS, producing a convoy (55 gates for 7 merges on 2026-09-06). Two delivered pieces make a shared train possible: the runtime tool `merge-train.sh` (chain "Merge train: a runtime tool builds, gates and records cumulative prefixes") turns an ordered candidate list into gated prefixes under `refs/anneal/train/<oid>` and a `merge-train-v1` record (`parseMergeTrainRecord` in `packages/db`), and the merge executor (chain "Merge executor: an authorization that names a train prefix is published as a fast-forward of main") publishes an authorization that carries a `train` object. This chain wires readiness to them behind a switch that is off by default, so the existing single-candidate tail stays the production path until an operator turns the train on.

Changes:
1. A new API environment variable `MERGE_TRAIN_WIDTH` (integer 0 to 3, default 0, validated at startup like the other API settings) enables the train when greater than 0 and bounds the number of candidates per train. With 0 the readiness worker's behaviour and every existing readiness, recovery and repair test are unchanged.
2. When the train is enabled, a readiness tick collects, per repository, every chain at merge readiness whose `readReadiness` stage is `ready` (valid exact-head PASS evidence) and whose recovery aggregate is not `REPAIRING` or `BLOCKED_DOWNSTREAM`, ordered FIFO by the time the Regression evidence was persisted. It forms a train when at least one candidate's evidence base differs from the live default-branch head (drift) or at least two candidates are ready; a single non-drifted candidate keeps today's single-candidate authorization path.
3. A train is one detached platform task of a new kind `merge-train` (created the way merge-tail repair tasks are created in `merge-tail-actions.ts`: chain-detached, `assigneeType: AGENT`, staffed by the Agent bound to the first candidate chain's Regression verification step, `maxSessionsPerTask: 1`) whose description instructs the session only to run `"${AGENTOS_TOOLS}/merge-train.sh"` with the candidate list the control plane wrote into the task's claim metadata (`baseSha`, `width`, ordered `candidates` with `taskId`, `chainId`, `headSha`, `branch`) and to finish; the session performs no other work. Every candidate chain's readiness task records a `mergeTail.train` marker naming the train task id and the candidate's position.
4. The merge lease is acquired for the train under the first candidate's chain lease target before the train task is enqueued and is held until the train settles (Change 6) or fails; a lease that cannot be acquired defers the tick as `withMergeLease` does today. While a train holds the lease no single-candidate readiness decision for that repository runs. A train task whose Run ends without a stored `merge-train-v1` record, or whose Run is lost, releases the lease, writes a `mergeTail.train` marker with `state: "aborted"` and the reason on every candidate, and returns the candidates to `ready` for a later tick; the train task itself is not retried.
5. When the train task stores a `merge-train-v1` record, readiness validates it with `parseMergeTrainRecord`, requires `record.baseSha` to equal the live default-branch head and every candidate `candidateHeadSha` to equal that chain's evidence `headSha`, and then, still under the lease, re-runs the existing second-read discipline once (`evaluateReadiness` per candidate with the train base) before authorizing. Candidates at positions 1..`contiguousPassCount` are authorized in position order with a `merge-authorization` output that carries the `train` object (`publishHead` = the prefix oid at `contiguousPassCount`, `predecessorOid` = that candidate's own predecessor, `ref`, `position`, `trainTaskId`) and are handed to merge execution exactly as `authorizeReadinessSettlement` hands off today. The lease is released after the last authorization is written; the executor's publication is not covered by it, as today.
6. Candidates outside the passing prefix settle as follows: the first `fail` prefix's candidate enters the existing gate-fix repair path through `enterRepair` with `headSha` = its candidate head and `baseHeadSha` = its predecessor prefix oid, charging the existing repair budget; a `no-verdict` prefix's candidate and every `skipped` candidate return to `ready` untouched for the next train; a `blocked` candidate enters the existing refresh-conflict recovery stop with the recorded reason. None of these paths runs a per-chain base-drift Regression re-run: `requeueRegressionSettlement` is not invoked for drift while the train is enabled.
7. Board and inbox: the train task renders as a card whose description lists the candidates and, after settlement, the record's verdict per position; each candidate readiness task's activity log receives one entry naming the train task, the position and the settlement; a `fail`, `blocked` or aborted train writes one inbox stop notice per affected candidate through the existing stop-notice upsert.
8. Documentation: a new `docs/adr/0004-publish-chains-through-a-merge-train.md` records the decision, the switch, the lease window and the settlement table from Change 6; `docs/operator-api.md` documents `MERGE_TRAIN_WIDTH`, the `merge-train` task kind, the `mergeTail.train` marker and the changed drift behaviour; `CONTRIBUTING.md`'s delivery section notes that chain publication follows the train when enabled.

Out of scope: the runtime tool and its record schema (already delivered), the executor's publication and replay logic (already delivered), `scripts/merge-train.mjs` and the host workflow, canonical templates and role prompts other than the train task description text, the repair budgets and repair task shapes, the approval gate on merge readiness (`isGatedMergeReadinessTask` keeps applying per candidate before authorization), any Prisma migration, and any change to behaviour when `MERGE_TRAIN_WIDTH` is 0.

Constraints: every state change runs in the same serializable transactions and chain locks the existing tail uses; the lease is never held by more than one train per repository and is always released on every exit path, including process restart (the deferred-release path in `merge-lease.ts` applies); a candidate is authorized only from a record whose `baseSha` is the live head at authorization time; semantic verification is not re-run for drift while the train is enabled, and the ADR states that trade-off explicitly; all failures are named, recorded and visible on the board and inbox, never silently retried.

Acceptance: `MERGE_TRAIN_WIDTH` unset or 0 leaves `merge-readiness-worker.test.ts`, the `merge-readiness-gate-*.dbtest.ts` suites, `merge-tail-readiness.dbtest.ts`, `merge-tail-repair*.test.ts` and `merge-tail-stop-notice.dbtest.ts` passing unchanged; new dbtests cover: two ready candidates form one train task with the expected claim metadata and lease marker; a stored record with `contiguousPassCount` 2 of 3 authorizes positions 1 and 2 with correct `train` objects and enters gate-fix repair for position 3 with the prefix predecessor as base; a `blocked` candidate enters the refresh-conflict stop; an aborted train releases the lease and returns candidates to `ready`; a record whose `baseSha` is stale authorizes nothing and releases the lease; a single non-drifted candidate still takes the single-candidate path; `MERGE_TRAIN_WIDTH` of 4 or `-1` is refused at startup with a named message. `npm run test -w @anneal/api` and `packages/db` tests pass; `npm run lint` is clean; the three documents in Change 8 are in the same diff.
