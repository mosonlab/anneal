Merge train: a runtime tool builds, gates and records cumulative prefixes for an ordered candidate list

Goal: a Run can turn an ordered list of chain heads into nested merge prefixes on the current base, gate every prefix concurrently on the configured gate slots, and persist one machine-readable train record that the control plane can authorize from.

Background: `scripts/merge-train.mjs` (ADR-0002) already implements the prefix algorithm for host windows: `buildPrefixes` creates cumulative `git merge --no-ff` commits in one worktree, strips `.chain/`, asserts the exact two-parent lineage `(predecessor, candidate head)`, blocks the rest of the list at the first conflict or already-contained candidate, gates each prefix through `packages/runner/runtime-tools/gate-worker/gate-dispatch.sh <prefix> --master <predecessor>` in parallel, and `contiguousPassingCount` picks the longest contiguous PASS prefix. It takes GitHub PR numbers from the operator, publishes by a raw fast-forward push, and holds the merge lease itself. None of that is reachable from a chain Run: the runner's runtime-tools bundle has no train tool, and the control plane (`packages/api/src/merge-readiness-worker.ts`) has no git workspace of its own. Chains therefore serialize through one lease and re-run Regression on every base drift (`requeueRegressionSettlement`, "Automatic base-drift recovery"); on 2026-09-06 that cost 55 gates for 7 merges. This chain delivers the workspace half only: a runtime tool with a persisted record. Nothing calls it yet; the lease, candidate selection and publication stay where they are today.

Changes:
1. A new runtime tool `packages/runner/runtime-tools/merge-train.sh` (with its implementation module beside the other runtime tools, and registered wherever the runtime-tool inventory lists tools so the bundle ships it) accepts a JSON candidate list on stdin: `{"schemaVersion":1,"baseSha":"<40>","width":<1..3>,"candidates":[{"taskId":"<regression task id>","chainId":"<uuid>","headSha":"<40>","branch":"<chain branch>"}]}` in FIFO order. It refuses malformed input, a `baseSha` that is not the current `origin/<default branch>` head, more than `width` candidates, and a candidate whose `headSha` is not the tip of `origin/<branch>`, each with a named reason and exit code 2.
2. The tool builds the nested prefixes in the Run workspace with the same rules as `buildPrefixes` in `scripts/merge-train.mjs`: prefix 1 = `baseSha` + candidate 1, prefix k = prefix k-1 + candidate k, `--no-ff` merge commits, `.chain/` stripped from the merge tree, exact two-parent lineage asserted after each merge. The first candidate that conflicts, or whose head is already an ancestor of the predecessor, is recorded as `blocked` with the reason and stops prefix construction; later candidates are recorded as `skipped`.
3. The prefix commits are pushed to `origin` under `refs/anneal/train/<prefixOid>` before any gate runs, so a later publisher can reach them by object id without this workspace. The push is append-only: an existing ref with a different target is a named failure, not a force update.
4. Every built prefix is gated concurrently through `gate-dispatch.sh <prefixOid> --master <predecessorOid>` using the Run's inherited gate environment (`AGENTOS_GATE_SERVER` or the `AGENTOS_GATE_PRIMARY_SERVER`/`AGENTOS_GATE_FALLBACK_SERVER` pair), at most `width` dispatches at once. Exit codes 75 and 76 (no verdict) are retried up to three times per prefix like `regression-verification.sh` does; a prefix with no verdict after the retries is recorded as `no-verdict` and is never treated as PASS.
5. The tool persists one `merge-train-v1` JSON record as the task step output through the runner's existing output path (`PUT /tasks/:id/output` as `regression-verification.sh finalize` uses it) and prints it on stdout: `{"schemaVersion":1,"baseSha","width","prefixes":[{"index","taskId","chainId","candidateHeadSha","predecessorOid","prefixOid","ref","verdict":"pass"|"fail"|"no-verdict","gateExcerpt"}],"blocked":[{"taskId","chainId","candidateHeadSha","reason"}],"skipped":[taskId...],"contiguousPassCount"}`. `contiguousPassCount` is the number of leading prefixes whose verdict is `pass`; a `fail` or `no-verdict` prefix ends the count even when a later prefix passed.
6. The record's schema is exported from `packages/db` next to the regression verdict schema (`parseRegressionVerdict`) as `parseMergeTrainRecord`, with the same fail-loud validation style, so the control plane can validate a stored record without importing runner code.
7. The tool is covered by a fixture test in the runner package modelled on `scripts/merge-train.test.mjs` (real bare `origin.git`, real worktrees, a fake `gate-dispatch.sh` on PATH that returns scripted verdicts): passing train of three, FAIL at prefix 2 (count 1), conflict at candidate 2 (blocked, candidate 3 skipped), already-contained candidate, stale `baseSha` refusal, no-verdict after retries, and the ref namespace push being append-only.

Out of scope: candidate selection, the merge lease (acquire, hold, release), creating or scheduling any task, authorizing or publishing a prefix, the merge executor, GitHub API calls, `scripts/merge-train.mjs` and its host workflow, `merge-readiness-worker.ts`, `readiness-decision.ts`, canonical templates and role prompts, the gate scripts themselves, and any change to the regression-verification tool or its `regression-verification-v2` output.

Constraints: the tool is a platform script with no model judgement inside; every refusal names its reason and exits non-zero; a prefix is only ever `pass` when `gate-dispatch.sh` printed `MERGE GATE: PASS <that prefixOid>` exactly; `.chain/` stripping, lineage assertions and conflict handling must match `scripts/merge-train.mjs` so a host train and a chain train prove the same thing; the runtime-tools bundle keeps shipping every existing tool.

Acceptance: `npm run test -w @anneal/runner` passes with the new fixture test covering all seven scenarios in Change 7; `packages/db` unit tests cover `parseMergeTrainRecord` accepting the record from Change 5 and rejecting a missing `contiguousPassCount`, a verdict outside the enum, and a `contiguousPassCount` larger than the leading pass run; the runtime-tool inventory test (or bundle test) lists `merge-train.sh`; running the tool against a fixture with a stale `baseSha` exits 2 and writes no ref; `npm run lint` is clean; `scripts/merge-train.test.mjs` still passes unchanged.

Route: implementation=senior-dev-astra-medium - gate dispatch, merge lineage assertions and the ref namespace push are a defense-list path whose hazards the fixture cannot fully witness
