Goal: a review, fix or regression step never claims against an implementation base commit that no remote carries, so one failed implementation Run can no longer strand the rest of its chain.

Background: `platformImplementationBaseSha` (`packages/db/src/run-open.ts:330-336`) pins the range every review sibling, fix step and regression step reads by taking the implementation Task's earliest Run with a non-null `baseSha`, ordered by `runNumber`, with no filter on that Run's status and no check that the commit is reachable on the repo remote. A Run records `baseSha` when it materializes the specification commit in its workspace, before it has pushed anything. When that first Run dies before its push - on 2026-09-06 three Runs died with `cli-missing (exit 127)` because the Mac runner plist inlined a RUNNER_PATH without `claude` - the recorded base stays local to a workspace that is later discarded. The chain's second, successful implementation Run pushes a different base, but the pin still names the dead one. Chain `c4148ba3` (branch `feat/readiness-requeue-counters`) hit this: implementation Task `cmtpng5ob0eevdbb1oa1fy6kh` Run 1 recorded `4f2e9e46ebfd811b023985cdac781f92caa30c14` (`Materialize direct-chain specification`, parent `0e89f922`, never pushed, 422 from the GitHub commits API), Run 2 recorded `ad36ac6e`, and both review steps then failed on the runner with `git failed (128): fatal: remote error: upload-pack: not our ref 4f2e9e46...`. Retrying reproduces it exactly, because the pin is derived, not stored per Run; the chain has no mechanical exit.

Changes:
1. `platformImplementationBaseSha` selects the earliest Run whose `baseSha` was actually published, not merely recorded. Add a persisted marker for that: the runner already reports the push, so record on the Run the fact that its base commit reached the repo remote, and let the selector require it. Keep `runNumber asc` ordering among the Runs that qualify, so the semantics the doc comment states - the chain's specification commit, not a recovery Run's head - are preserved.
2. When no Run qualifies, keep failing loud through the existing `PinnedBaseCommitError` path with a reason that names the implementation Task and says no Run published a base, so the candidate parks in Backlog with a readable message instead of failing on the runner with a raw git error.
3. When a claim is refused because the pinned base is unpublished, the `TaskActivity` and the Inbox message carry the offending sha and the implementation Task id, so an operator can tell this apart from a transport failure without reading the database.
4. Backfill is not required, but the selector must tolerate rows written before the marker existed: a Run with no marker and a successful outcome counts as published; a Run with no marker and a failed outcome does not.

Out of scope: the runner-side cause of the 2026-09-06 `cli-missing` failures (chain `99fa42a5` owns the Mac runner plist RUNNER_PATH rendering); any change to how the specification commit is materialized or to `implementationHeadFromOutput`; base-drift recovery and its retry classes (chain `e9d6a143`); recovering chain `c4148ba3` itself, which is being re-instantiated by hand.

Constraints: purely a selection and reporting change - no Run is rewritten, no base is repaired after the fact, and a claim never silently falls back to a different base than the one the selector names. Fail loud: an implementation Task with no publishable base parks its dependents rather than letting them reach a runner.

Acceptance: a dbtest builds an implementation Task with Run 1 failed and holding an unpublished base and Run 2 succeeded holding a published one, and asserts the pinned range names Run 2's base; a dbtest with only an unpublished base asserts the claim is refused with `PinnedBaseCommitError`, the task parks in Backlog, and the activity metadata carries the sha and the implementation Task id; a dbtest with pre-marker rows asserts the succeeded-Run fallback; `npm run test -w @anneal/db` and `npm run test -w @anneal/api` are green.

Route: implementation=senior-dev-opus-high - the pinned base feeds every review, fix and regression step of every chain; a wrong selector strands whole chains with an unreadable git error
