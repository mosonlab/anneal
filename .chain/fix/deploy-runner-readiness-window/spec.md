Deploy: a control-plane deploy is green only when the API and every local runner are registered and stay healthy

Goal: after the VM control-plane deploy restarts services, the deployment is reported successful only when the API answers and all local runners on that host have re-registered on the new build and every service stays active for a minimum observation window; a deploy that leaves runners silently dead escalates instead of reporting green.

Background: `scripts/deploy/quiet-window-deploy.mjs` `verifyServices` (`:1019-1070`) checks each unit with `systemctl is-active` and, for the control-plane role, only probes the API `/health` and `/version` (`:1052-1070`). The runner registration verification that checks each local runner has re-registered with the deployed commit (`runner-role-verification.mjs`) runs only when `deployRole === "runner"` (`:1022`), although `localRunnerIds` is already computed for both roles (`:726`). Production is one VM running control plane plus 16 `vm-runner-*` units; Mac hosts are runner-only and do get the check. Two consequences: (1) a change that breaks runner startup or registration but not the API deploys green and every chain stalls with no escalation; (2) the loop returns on the first all-green sample (`:1019-1052`), so a unit that starts and crashes after a second, or a process that stays `active` but never registers, is not caught. The rollback path's readiness check (`:676-686`, used via `:707` and `:1106`) has the same control-plane-only shape. `apiBaseUrl`/`operatorToken` are null for the control-plane role (`:730-731`) and `loadEnvironment` only requires `OPERATOR_TOKEN` for the runner role (`:336-337`).

Changes:
1. Run the local runner registration verification for both deploy roles. For the control-plane role, target the loopback API (`127.0.0.1:${API_PORT}`) with `OPERATOR_TOKEN` read from the deployment's `.env`; a missing token on a control-plane host that has local runners is a preflight failure, not a skipped check.
2. Make the control-plane readiness require both the API probe and the runner registration check; do not replace one with the other.
3. Add a minimum observation window: after the first all-green sample, keep sampling `is-active` for all units and the API probe for a configurable minimum (default 20 seconds, environment-overridable) and fail if any sample regresses. Keep the existing overall timeout as the upper bound; raise it if the minimum window requires.
4. Apply the same combined check to the rollback verification (`verifyRecoveredServices`) so a rollback also proves runners are back.
5. Record the verification outcome (units checked, runners registered, window duration) in the deployment ledger entry and mention the new criteria in `docs/runbooks/quiet-window-auto-deploy.md`.

Out of scope: the quiet-window wait deadline and alerting (D-04), escalation scope per commit (D-03), an operator `--rollback` CLI mode (D-01), the launchd installer and wrappers (`install-launchd*.mjs`, `launchd-service-wrapper*`), `service-inventory.mjs` unit lists, and any change to what a runner registers.

Constraints: no `systemctl` or launchd call outside the existing `service-control.mjs` seam; the check must work on both systemd and launchd hosts through that seam; a verification failure escalates through the existing escalation path with a reason naming the failing unit or unregistered runner id; no self-healing.

Acceptance: `npm run test:auto-deploy` is green; new fixtures in `scripts/deploy/quiet-window-deploy.test.mjs` cover: control-plane role with one local runner never registering fails with a reason naming that runner id; control-plane role where a unit flips to inactive inside the observation window fails; both roles pass when API, all runners, and the window are green; the rollback path fails when a runner does not re-register. `docs/runbooks/quiet-window-auto-deploy.md` states the combined criteria and the default window.

Route: implementation=senior-dev-opus-medium - operator chose Claude capacity; the readiness rule is fully specified and the harness fixtures can witness every branch
