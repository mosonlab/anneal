Deploy: automatic deploys coalesce on a minimum interval, the dispatch drain does not stop mechanical merge and readiness work, and the release target is main at deploy time

Goal: main advancing no longer starts a deploy attempt every five minutes. Automatic deploys land at most once per configured interval (default 4 hours) unless a natural quiet window appears sooner; a dispatch drain, when one is still needed, stops only claims that would start an agent session, so merge execution and readiness keep flowing during the drain; and the release deployed is the main head read when the quiet window is actually obtained, not the one read when the tick began.

Background: on 2026-09-07 the VM control plane ran the first unattended deploy cycles after PR #578 (deploy-wait budget drains dispatch). Observed: 13:00Z tick targets 89a1591e; 13:45Z wait budget (45 min) exceeded -> `DispatchDrain` row -> 14:00Z barrier -> 14:03Z deployed; the next tick immediately targets 7046bc85 (main had moved during the drain), waits 45 min again, 14:49Z second drain, 15:14Z barrier, deploy. Main was already 82081eae by then, so a third cycle follows. During each drain `run-claim.ts:313` refused every claim with `dispatch-draining`, including the merge executor's mechanical merge runs (executor journal: repeated 409), so chain 2e621a8a's authorized merge (PR #577, readiness authorized 14:54Z, Chain Lease handed to the queued Run) sat queued; the lease handoff expired unconsumed after 81 s and d3520ecf's readiness acquired and released the lease twice for nothing. Net effect: every merge forces a deploy, every deploy drains the fleet for up to 45+ min and blocks the next merge, so merge-tail throughput is capped near one PR per deploy cycle, and the operator Inbox shows `自动部署失败于 7046bc8 · quiet-window-wait-exceeded` for what is the drain's normal path, not a failure. Deploying every main advance is not required: production only needs the platform fixes eventually, and an operator can still deploy on demand with the existing script.

Changes:
1. Cadence: `scripts/deploy/quiet-window-deploy.mjs` records the last successful automatic deploy time (in the existing deployment state under `.agentos-deploy`) and, when main has moved, a tick deploys only if either the interval since the last automatic deploy is at least `AUTO_DEPLOY_MIN_INTERVAL_MINUTES` (default 240) or the quiet window is already open (blockers=0) at tick time; otherwise it logs `NOOP coalescing next-eligible=<time>` and exits. The wait budget and drain are entered only once the interval has elapsed. Both hosts read the same setting from `shared/.env`.
2. Drain scope: `DispatchDrain` refuses only claims that would start an agent session. Mechanical merge-execution Runs and readiness evaluation are admitted during a drain (they are already covered by the deploy barrier, which is the exclusive half taken when the deploy actually starts). `run-claim.ts` distinguishes the two by the Run's step kind, not by runner identity. `blockingRuns` in the deploy script keeps counting only agent Runs, as today.
3. Target: after the quiet window (or barrier) is obtained, re-read `origin/main`; if it moved past the tick's target, deploy the new head (build the artifact for it) rather than the stale one; log `target-advanced from=<old> to=<new>`.
4. Inbox wording: the wait-exceeded notice that starts a drain is sent as an informational message (`自动部署等待超时，已开始排空派发`), not as a deploy failure; the failure kind stays for real failures.
5. `docs/runbooks/quiet-window-auto-deploy.md` and `docs/operator-api.md` (the `dispatchDrain` field and the claim refusal) document the interval, the drain scope, and the target re-read.

Out of scope: changing the wait budget or drain deadline defaults; runner-role (Mac) deploy logic beyond reading the same interval; a manual deploy trigger (the existing script already is one); web UI changes beyond the Inbox message kind.

Constraints: the deploy barrier semantics are unchanged; a Run already claimed is never interrupted; the interval is a floor, not a schedule, so a genuine quiet window still deploys early; no new database tables (the drain row gains no columns; scope is decided from the Run being claimed).

Acceptance: hermetic auto-deploy tests: a tick with main moved and last deploy 1 hour ago and blockers>0 exits NOOP coalescing; the same tick with blockers=0 deploys; a tick 5 hours after the last deploy enters the wait budget; a dbtest shows a mechanical merge Run and a readiness evaluation admitted while an unexpired drain row exists and an implementation Run refused with `dispatch-draining`; a test where main advances between tick start and barrier deploys the new head and logs `target-advanced`; the runbook and handbook snapshot tests pass.

Route: implementation=senior-dev-astra-medium - hazard tier (alters merge automation admission and the deploy barrier path), same class as PR #578: a wrong drain scope can deploy into a live merge or drain the fleet
