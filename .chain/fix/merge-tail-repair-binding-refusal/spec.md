Goal: a merge-tail repair that the platform can no longer settle is refused when it is opened, with a reason an operator can act on, instead of being handed to an agent that does the work and then cannot report it.

Background: `activeRepairRecoverySourceRun` (`packages/api/src/merge-tail-actions.ts`, `merge-tail-actions.js:165` in the deployed release) throws a bare `Error` - `Merge recovery <recoveryId> is not bound to repaired Run <runId>` - and it is called from `commitWithLeaseOutcome.release` inside `completeRun`'s transaction (`run-completion.ts`, `merge-lease.ts`). Nothing between there and the runner route classifies it, so the runner's completion POST answers `500 {"error":"Internal server error"}` and the Run is recorded as an external failure. The work is already committed to the branch at that point, so the repair is unreportable and the next attempt reproduces it exactly. On 2026-09-06 chain `97008bbe` (`fix/executor-ref-update-uncertain`) hit this twice: gate-fix repair task `cmtpvlqcw0a2ydb3ex2zpfyga` Run 1 committed the fix at `9bda965d` and failed to complete at 14:04Z, Run 2 re-verified the same commit and failed identically at 14:50Z, exhausting `maxSessionsPerTask`, leaving the regression task saying `gate-fix repair ... failed without closing the repair` with no mechanical exit. The state that makes the invariant false is two merge-tail mechanisms overlapping on one chain: the tail task carried base-drift recovery `cmtpu9wrz00e0db3e3uy87vrb` bound to source Run `cmtpu8zma009xdb3e5jd6sdbc`, while the gate-fix repair was opened against the regression step's Run `cmtpujio103bedb3euucxxdxx`. Two paid Runs were spent producing work the platform then refused to accept.

Changes:
1. Check the binding when a repair is opened, not only when it settles. `POST /tasks/:taskId/merge-tail/repair` and the automatic repair path both refuse to create a repair task whose recovery is not bound to the Run being repaired, with a named refusal that reaches the operator through the existing stop-notice route.
2. At settlement, turn the invariant violation into a classified, non-500 outcome: the completion is rejected with a named reason the runner records on the Run, and the repair task is parked with that reason rather than counted as an external failure. A bare `Error` escaping `completeRun`'s transaction is the defect; nothing about this state is an internal server error.
3. Record the binding mismatch as a `TaskActivity` on the regression task carrying the recovery id, the bound source Run id and the repaired Run id, so the two overlapping mechanisms are visible without reading the API journal.
4. Give a stranded repair an operator exit: document in `docs/operator-api.md`, beside the existing repair-budget recovery section, how to settle a chain whose repair cannot bind, and make that route work for a task whose session budget is already exhausted.

Out of scope: the base-drift recovery classifier and its retry classes; whether a chain should be allowed to run base-drift recovery and gate-fix repair at the same time (name the overlap, do not redesign it here); the repair budget constant `MAX_MERGE_TAIL_REPAIR_ATTEMPTS`; the flaky merge-executor readiness test the stranded repair happened to be fixing; recovering chain `97008bbe`, which is being delivered by hand.

Constraints: fail loud but classified - no path may answer 500 for a state the platform can produce itself; the refusal at open time must not silently drop a repair that is legitimately bound; no change to how a correctly bound repair settles today.

Acceptance: a dbtest builds a recovery bound to Run A and requests a repair for Run B, and asserts the repair is refused at open with the named reason and no repair task is created; a dbtest forces the mismatch at settlement and asserts `completeRun` answers a classified rejection rather than throwing, the Run carries the reason, and the task parks; a test asserts the `TaskActivity` carries all three ids; `npm run test -w @anneal/api` is green and `docs/operator-api.md` documents the operator exit.
