Goal: a chain step whose specification read is merely slow because the host is loaded waits and then runs, instead of being parked in Backlog for an operator to retry by hand.

Background: before a review or fix candidate is claimed, the control plane re-reads the specification from the repository to verify fidelity. `readSpecificationAtHead` in `packages/api/src/specification-fidelity.ts:375-435` gives every attempt the same fixed deadline - `SPECIFICATION_READ_ATTEMPT_TIMEOUTS_MS = [1_200, 1_200, 1_200]` - and turns a deadline hit into a `GitHubReadError` of kind `timeout`, classified transient. `run-claim.ts:518-600` then defers the queued Run at 15 s, 30 s and 60 s inside a fixed `SPECIFICATION_READ_DEFERRAL_BUDGET_MS` of 5 minutes, and on exhaustion `exhaustTransientSpecificationRead` parks the task in Backlog with `spec-transcription-unreadable`. The three deadlines are identical, so a host whose reads take longer than 1200 ms fails all of them for the full budget and the outcome is deterministic, not probabilistic: on 2026-09-06 with VM load average around 33, L1 step 3 `cmtpn8fxu0dhndbb12pquer14` and L5 step 3 `cmtpn8gqt0dk7dbb1bss7t5oa` both parked this way and both succeeded on a plain retry once load fell. A parked task is a manual step in an otherwise unattended loop, and the parking reason names an unreadable specification, which is misleading: the specification was readable, the deadline was not.

Changes:
1. Make the per-attempt deadlines an escalating ladder instead of three identical values, so a read that is slow rather than broken completes on a later attempt within the same claim. State the ladder as one named constant with the reasoning in its doc comment.
2. Distinguish, inside the deferral budget, a budget whose failures were all of kind `timeout` from one that saw any other transient failure. For the all-timeout case, extend the deferral window past `SPECIFICATION_READ_DEFERRAL_BUDGET_MS` up to a second, larger documented ceiling, still deferring at the longest delay, and park only when that ceiling is reached. Any non-timeout transient keeps today's 5-minute budget and today's parking behaviour.
3. When an all-timeout budget is extended, open exactly one Inbox notice for the task the first time it happens and none afterwards, so a sustained overload is visible without one message per deferral.
4. When such a task is finally parked, the refusal message says the read exceeded its deadline under load and names the observed attempt count and elapsed window, rather than reporting the specification as unreadable.
5. Document both ceilings and the timeout-versus-other-transient split in `docs/operator-api.md` beside the existing claim refusal reasons.

Out of scope: the fidelity comparison itself and what counts as a mismatch; the server-side content reader implementation and its remote access path; runner-side claim behaviour and lease timing; any change to admission control, `RUNNER_CLAIM_MAX_LOAD_AVERAGE`, or how many runners are allowed to claim concurrently; the separate pinned-implementation-base defect.

Constraints: no silent success - a read that never completes still ends in a loud, parked task with a reason that names the deadline; the extended window is bounded by a constant in the source, never unbounded; behaviour for non-timeout transients is unchanged; no new configuration surface beyond the named constants unless an item above requires it.

Acceptance: a unit test drives `readSpecificationAtHead` with a reader that returns after the first deadline but before the last and asserts the read succeeds; a dbtest with a reader that always exceeds the deadline asserts the candidate defers past 5 minutes, stays QUEUED, opens exactly one Inbox notice, and parks only at the larger ceiling with a refusal message naming the deadline; a dbtest with a non-timeout transient asserts the 5-minute budget and today's parking reason still apply; `npm run test -w @anneal/api` is green and `docs/operator-api.md` carries both ceilings.

Route: implementation=senior-dev-opus-medium - a bounded change to one claim-stage deadline and its transient budget, with the failure mode already reproduced twice
