Merge readiness: base-drift requeues after a valid Regression PASS are not bounded by the lease-loss refund cap, and an operator retry resets the cap

Goal: a Chain whose Regression PASS is valid reaches authorization once the merge lease is free and GitHub answers; it is never parked for good because main moved while it waited, or because earlier external failures in the same task already spent a shared counter.

Background: `Run.leaseLossRefunds` (cap `LEASE_LOSS_REFUND_CAP` = 3, `packages/db/prisma/schema.prisma` ~1131) is currently one counter shared by three platform refunds: a Runner losing its Run lease, a late-salvage claim invalidation, and the merge-tail requeue that readiness issues when a PASS goes stale (`requeueRegressionSettlement` → `requeueMergeTailRun` with `budgetGrant: 1`, `packages/api/src/merge-readiness-worker.ts` ~387-453, `packages/api/src/merge-tail-state.ts` ~209-228). Provider-transport and Regression target-fetch external failures use the separate `EXTERNAL_FAILURE_REFUND_CAP` and `retry-after-completion` path (`packages/db/src/run-open.ts` ~37-40, ~871-884; `packages/api/src/run-completion.ts` ~193-209, ~1003-1013), so they do not spend `leaseLossRefunds`. Lease contention and lease transport deferral themselves do not spend it (`recordContention` ~1100-1122 and `recordLeaseDeferral` ~832-858 in `packages/api/src/merge-readiness-worker.ts`); they only lengthen the wait during which main moves. On 2026-09-07 chain 3c6e4dc3 (PR #558) reached refund 3 on its Regression task by 06:01Z (base-drift requeues; git TLS external failures use the separate external-failure cap), then at 07:38Z passed against d3b1d0ad, waited on the lease (contended ×3, transport deferred ×2, other operators delivering by hand), and at 07:50Z, when main had moved to 200546ad, readiness could not requeue: `Merge-tail target was not queued: Lease-loss refunds exhausted after 3 platform-refunded attempts`. The documented recovery (`PATCH /tasks/:taskId` setting `maxSessionsPerTask` + `POST /tasks/:taskId/retry`) re-ran Regression to PASS at 09:05Z, but the counter was not reset, so the next stale PASS at 09:11Z was refused again. The only exit was a manual worktree merge, remote gate and fast-forward push. Regression task `cmtqletgt004ddb0i2g0hoihd`, readiness task `cmtqletgv004fdb0i3yezah70` carry the TaskActivity and Run rows (`Run.budgetGrants`, `Run.leaseLossRefunds`).

Changes:
1. A readiness base-drift requeue of a Regression task whose PASS was valid at its exact base (the control plane invalidated it after a remote read, the agent did nothing wrong) does not spend `leaseLossRefunds`. It is bounded on its own: reuse the existing base-drift recovery ceiling where the requeue happens inside a recovery, and a per-task readiness requeue bound with a named stop where it does not; the stop reason names the count and the ceiling.
2. `POST /tasks/:taskId/retry` on a Regression task refused with `Lease-loss refunds exhausted` resets `leaseLossRefunds` for that task and records the reset as a TaskActivity, so the documented recovery works once instead of failing on the next stale PASS.
3. `docs/operator-api.md`: the "Lease-loss retry refused" section states which Run births spend the cap and that an operator retry resets it; the readiness section states the requeue bound and its stop.

Out of scope: the Runner lease-loss and external-failure refund paths themselves; the executor-offline wait (PR #560); merge train (chain 73607a7a); reusing the semantic verdict after drift (R3, chain 13276965).

Constraints: no new environment variable; a genuine Runner lease-loss loop stays bounded at 3; a Chain outrun by main forever still stops with a named reason, never spins; dbtests run on the merge gate only.

Acceptance: a dbtest drives a Regression task to `leaseLossRefunds = 3` through three Runner lease-loss refunds, followed by an external-failure refund that preserves the exhausted counter, then a valid PASS goes stale during lease contention and base drift, and asserts the requeue is admitted and the counter unchanged; a dbtest exhausts the new requeue bound and asserts the named stop; a dbtest exhausts the cap through Runner lease losses, applies `PATCH` + `retry`, and asserts the counter is 0 and the activity written; `npm run test -w @anneal/api` and `-w @anneal/db` green; `npm run lint` clean.
