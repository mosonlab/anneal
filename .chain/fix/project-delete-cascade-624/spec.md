API: Deleting a Project removes every row it owns

After this chain, `DELETE /projects/:projectId` succeeds on any Project, whether freshly bootstrapped or carrying chains, Runs and staffing decisions, and leaves no row belonging to that Project behind (fixes #624).

Background: `DELETE /projects/:projectId` (`packages/api/src/routes/admin.ts`, `registerAdminRoutes`) is a bare `db.project.delete()`. The Prisma schema (`packages/db/prisma/schema.prisma`) cascades most project-owned models from `Project`, but several edges between those models are `onDelete: Restrict` on purpose, and PostgreSQL checks `RESTRICT` per row at the moment the referenced row is deleted, so the single-statement cascade aborts as soon as it reaches an Agent, Task, Run, Goal or Repo that another row still references. The reporter hit `StaffingProfileEntry_assigneeAgentId_fkey` (P2003) on a Project with zero repos and zero tasks: `createProjectBootstrap` (`project-bootstrap.ts`) writes the workflow Agents and a `Default` StaffingProfile whose entries and tiers reference them, so every bootstrapped Project is undeletable. A Project with history fails on the next Restrict edge instead. The Restrict edges to Agent, Task, Run, Goal and Repo are: `StaffingProfile.mergeTailRepairAgent`, `StaffingProfileEntry.assigneeAgent`, `StaffingProfileTier.agent`, `Task.assigneeAgent`, `Task.repo`, `Task.goal`, `Task.goalDecisionRun`, `Task.dispatchAfter` (self), `Task.goalPredecessorTask` / `Task.goalPredecessorIdentity` (self), `Run.task`, `Run.goal`, `Run.agent`, `Run.repo`, `Run.retryOfRun` (self), `Run.goalLineageTask`, `Session.agent`, `Session.task`, `Session.goal`, `GoalExecutionEvent.goal` / `.task` / `.run` (plus identity variants), `MergeLeaseEvent.handedOffRun`, `TaskTemplate.webhookRepo`, `Agent.environment`. The schema comment above `StaffingProfileEntry` explains why these are Restrict: deleting one Agent must not silently drop an operator's staffing decision. That reasoning is about single-row deletes; a Project delete removes the decision together with everything it applied to. The route currently surfaces the failure as a bare 500 `{"error":"Internal server error"}`; the web console's confirmation (`projects.confirm.delete` in `apps/web/src/locales/en.ts` and `zh.ts`) already promises the cascade. A nonexistent id also answers 500 today (Prisma P2025 escapes the route).

Changes:
1. `DELETE /projects/:projectId` deletes the Project and every row owned by it inside one database transaction, in an order that never triggers a `Restrict` edge listed in Background: rows that reference a Project-owned row through a Restrict edge are removed before the row they reference, and nullable self-references (`Task.dispatchAfterTaskId`, `Task.goalPredecessorTaskId`, `Task.goalDecisionRunId`, `Run.retryOfRunId`, `MergeLeaseEvent.handedOffRunId`, `TaskTemplate.webhookRepoId`, `StaffingProfile.mergeTailRepairAgentId`) are cleared before their target rows are deleted. Every delete and update in that transaction is scoped to the Project by `projectId`, or by a relation whose root carries that `projectId`, so no row of another Project is touched.
2. The deletion logic lives in a named function in its own module under `packages/api/src/` (not inline in the route), taking the Prisma client and the project id, so the route stays a thin binding.
3. The route answers `404 {"error":"Project not found"}` when no Project has that id, matching the existing `GET /projects/:projectId` message, and `204` with an empty body on success.
4. No `onDelete` value, model, or migration changes in `packages/db/prisma/schema.prisma`; the Restrict edges keep protecting single-row deletes.
5. `docs/operator-api.md`, section `DELETE /projects/:projectId`, states that the delete removes every row the Project owns (agents, repos, templates, staffing profiles, tasks, runs, sessions, goals, inbox items, chain controls, merge leases) in one transaction, and lists the `404` response.
6. A new `packages/api/src/project-delete.dbtest.ts` (following the fixture conventions of `project-bootstrap.dbtest.ts`) covers: (a) a Project created through `POST /projects` with nothing added answers 204 and afterwards no `Agent`, `StaffingProfile`, `StaffingProfileEntry`, `StaffingProfileTier`, `TaskTemplate`, `TaskTemplateStep`, or `Environment` row carries its id; (b) a Project with a chain instantiated from its direct template, at least one Run with its Session, at least one Task whose `dispatchAfterTaskId` points at another Task of the same Project, and at least one Run whose `retryOfRunId` points at another Run of the same Project answers 204, and afterwards every model that has a `projectId` column has zero rows for that id; (c) a second Project created in the same test with its own bootstrap rows and one Task is untouched by (b): its row counts per model are identical before and after; (d) an unknown id answers 404 with the body in Change 3.

Out of scope: `DELETE /repos/:repoId` and `DELETE /agents/:agentId`, which have the same bare-delete shape (report in the PR description as a follow-up, do not change them); any schema, migration, or `onDelete` change; deferrable constraints; a typed 409 for a blocked delete (the delete is not blocked after this change); changing the web confirmation copy; archiving or soft-deleting Projects; refusing deletion while a Run is active (the operator's confirmation is the guard today); any change to `createProjectBootstrap`.

Constraints: The transaction fails loudly and rolls back as a whole if any statement fails; no partial deletion and no silent skip of a table. No raw SQL `TRUNCATE` or `SET CONSTRAINTS`; use Prisma model operations scoped by `projectId`. The function must not enumerate tables dynamically from `pg_tables`; each model it touches is named in code so a future model with a Restrict edge fails the dbtest rather than being silently missed. Database tests are merge-gate evidence and are not run inside the Run.
