Deploy: a release artifact verifies with only the files every previous builder ships

Goal: an operator can deploy any commit of main from the previously deployed release, because a release's own artifact verifier never imports a file that an older builder did not put in the artifact.

Background: `deployReleaseArtifact` builds the target's artifact with the code of the release that is currently deployed, then calls `loadTargetVerifier` (`scripts/deploy/release-artifact.mjs:183-204`), which `require()`s the target's own copy of `scripts/deploy/release-artifact.mjs` out of the freshly built artifact directory and runs its `verifyReleaseArtifact`. Verifying the target with the target's verifier is deliberate. What is not deliberate is the coupling it creates: the target's verifier can only load if every module it imports was copied by the older builder that produced the artifact. Commit `b6532a97` (PR #514, merged 2026-09-06 09:19Z) added `import { RUNTIME_TOOL_FILES, expectedDirectoryEntries } from "../../packages/runner/scripts/build-runtime-tools.mjs"` to `release-artifact.mjs` and added that same path to `DEPLOY_RELEASE_EXTRA_ARTIFACT_PATHS` in `release-artifacts.mjs`. The production release deployed at the time, `6443970987de7649459f5cdddcc6bfe94cfecdb4`, predates the second half of that change, so its builder does not copy `packages/runner/scripts/`, and loading the new verifier out of the artifact it built fails with `ERR_MODULE_NOT_FOUND`. On 2026-09-06 13:12:40Z the production auto-deploy escalated with `reason=release-artifact-invalid detail=target-verifier-ERR_MODULE_NOT_FOUND` and every commit of main at or after PR #514 is undeployable on both hosts, including the fix for this defect, because the artifact that carries the new path list can never be verified by the old one. `scripts/deploy` is copied as a whole directory and has been in every builder's path list, so a module that lives there is reachable from any artifact an older builder produced.

Changes:
1. Move the runtime-tool inventory declaration - `RUNTIME_TOOL_FILES` and `expectedDirectoryEntries` - out of `packages/runner/scripts/build-runtime-tools.mjs` into a new module under `scripts/deploy/`, keeping it a pure declaration with no filesystem access. Both consumers import it from there: `packages/runner/scripts/build-runtime-tools.mjs` re-exports it so the runner build keeps its current import surface, and `scripts/deploy/release-artifact.mjs` imports it directly instead of reaching across into `packages/runner`. The inventory stays declared exactly once, which is what PR #514 established.
2. State the constraint the defect broke as a rule in `scripts/deploy/release-artifact.mjs` beside `loadTargetVerifier`: the verifier's module graph may only reach Node builtins and modules inside `scripts/deploy/`, because an older builder decides which files exist in the artifact it produced.
3. Add a check that enforces rule 2 mechanically. Resolve the static import graph of `scripts/deploy/release-artifact.mjs` transitively and fail when any resolved specifier lands outside `scripts/deploy/` and is not a Node builtin. Name the offending importer and specifier in the failure.
4. Leave `packages/runner/scripts/build-runtime-tools.mjs` in `DEPLOY_RELEASE_EXTRA_ARTIFACT_PATHS`. It is correct for the artifact to carry it; the defect is that the verifier depended on it before every builder shipped it.

Out of scope: how the runner builds or copies runtime tools at build time, and the contents of `RUNTIME_TOOL_FILES` itself; the gate-worker scripts those entries name; the quiet-window blocker rule, escalation handling, or any other deploy phase; recovering the escalated production deploy, which the operator clears by hand once this lands; the merge-executor follower and its own release adoption path.

Constraints: the change is a relocation plus a guard, not a behaviour change - the inventory the build and the deploy verifier see must be identical to today's, entry for entry and directory for directory. Fail loud: the new check reports the first violating edge rather than skipping unresolvable specifiers. The new module must not import anything outside Node builtins, so that it is loadable in an artifact built by any release.

Acceptance: the new check is part of a suite the merge gate runs, is red when a test fixture adds an import of a module outside `scripts/deploy/` to the verifier graph, and is green on the tree; a test asserts `expectedDirectoryEntries()` and `RUNTIME_TOOL_FILES` are unchanged in content from the current declaration; `npm run test -w @anneal/runner` and the `scripts/` deploy suites are green; `npm run lint` and `npm run lint:types` are green.

Route: implementation=senior-dev-opus-high - production deploy is down and this is the only path that restores it; the change sits inside the release verifier, where a second mistake costs another undeployable release.
