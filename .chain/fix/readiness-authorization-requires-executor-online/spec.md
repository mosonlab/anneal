Merge readiness: an authorization is written only while a merge executor is online, otherwise readiness requeues itself

Goal: a chain that is ready to merge waits at readiness while no merge executor can claim its authorization, instead of being authorized against a base that will have moved by the time an executor returns.

Background: readiness and the executor are decoupled today. `packages/api/src/merge-readiness-worker.ts` (`authorizeReadinessSettlement`, the leased `authorize` decision around `:836`) writes the authorization through `produceMergeAuthorization` (`packages/db/src/merge-authorization.ts:65`) whenever the regression evidence is fresh, whether or not any runner in `mergeExecutorRunnerIds()` (`packages/db/src/merge-integrator-db.ts:1079`) is alive. When the executor is down (contract-mismatch crash loop, follower restart, an operator drain), authorizations pile up; on restart the first one merges and every other one stops with `Mechanical merge stopped: base-drift`, each costing a full base-drift recovery (regression plus gate, p50 114 minutes). Measured on 2026-09-06: 35 base-drift stops at four executor outages, 12 of which then flipped their semantic verdict on rerun. Measured again during drain #2 on 2026-09-07: three authorizations written after `systemctl stop`, two of which drifted on restart. Report of record: `records/anneal/reports/REPORT-merge-tail-throughput-20260907.md` §2 and R2. Daemon liveness already exists: `packages/api/src/runners.ts` (`DaemonSnapshot.online`, the `lastSeenAt` window at `:46`) is what `GET /runners` reports.

Changes:
1. Before the leased `authorize` decision is applied, readiness checks that at least one runner id from `mergeExecutorRunnerIds()` is `online` under the same rule `GET /runners` uses. If none is, readiness settles as `requeue` (the existing `requeueRegressionSettlement` path, `:294`), records a TaskActivity naming the reason (`merge-executor-offline`) and the executor runner ids it checked, and does not write an authorization. The regression evidence is untouched; no Run is opened.
2. The requeue is bounded the same way other readiness requeues are bounded today; it must not create an unbounded loop and must not consume regression repair budget. If an existing ceiling applies, reuse it; if the ceiling is reached, the tail parks in REVIEW with a failureReason that names the executor outage, exactly like other readiness stops.
3. When the executor allowlist is empty (`MERGE_EXECUTOR_RUNNER_IDS` unset), behaviour is unchanged: the check is skipped and authorization proceeds as today. Fail loud only on a configured allowlist with no online member.
4. `docs/operator-api.md`: the readiness section states the new precondition and the activity it writes; the runbook text that tells an operator to drain by stopping the executor is replaced by "an executor that is offline stops new authorizations by itself; drain by holding chains, not by stopping the executor". Only the sentences that become inaccurate change.

Out of scope: the merge lease protocol and its timeouts; merge-train; the executor's own base-drift handling and recovery path; `GET /runners` semantics; deployment scripts and the follower timer.

Constraints: one decision point, in the readiness worker, using the existing daemon liveness function rather than a second liveness rule; no new configuration surface; every skipped authorization leaves a TaskActivity; dbtests run only on the merge gate.

Acceptance: `npm run test -w @anneal/api` and `-w @anneal/db` green. A dbtest with `MERGE_EXECUTOR_RUNNER_IDS` naming a runner whose `lastSeenAt` is outside the online window shows readiness settling as requeue with the named activity and no `MergeAuthorization` row; the same test with the runner inside the window shows the authorization written as today; a test with the allowlist unset shows authorization written regardless of daemon state. Handbook updated in the same diff.

Route: implementation=senior-dev-opus-medium - operator chose Claude capacity; a single guarded decision point with mechanical acceptance
