Deploy: a retryable-transient escalation at its retry cap expires after a backoff instead of stopping every later tick until an operator runs `--clear-escalation`; a transport-caused artifact build failure is classified retryable

Goal: the quiet-window auto-deploy never stays stopped on a failure it has already classified as transient; a source-remote read timeout, a TLS handshake reset or a clone that failed on transport costs a bounded backoff, not an operator visit.

Background: `scripts/deploy/quiet-window-escalation.mjs` classifies a marker into `retryable-transient` / `commit-scoped` / `host-scoped` (`escalationScope`, ~33-56). Under the retry cap a retryable-transient marker already self-clears on the next successful attempt (~75-100); once `attempts >= retryCap` it latches and every later tick logs `STOP escalation-active scope=retryable-transient` (~101-130) until an operator runs `quiet-window-deploy.mjs --clear-escalation`. On the Mac runner host on 2026-09-07 this happened four times in three hours (`source-remote-read-timeout` 02:23Z, 02:30Z, 02:47Z, 02:53Z), each during a GitHub transport jitter window that was over within minutes. Separately, `release-artifact-build-failed` is commit-scoped today whatever its cause: the VM escalated on it twice (09:38Z building 4a44a44f, 10:00Z building 00fc93a8) because the artifact clone hit `gnutls_handshake() failed`; both needed a manual clear although main had already moved past the commit. The commit-supersession path (`quiet-window-deploy.mjs` ~127) does not help when the failure is reading the source at all.

Changes:
1. A retryable-transient marker that has reached the retry cap carries a `retryAfter` timestamp computed from the attempt count with capped exponential backoff (source constants; first retry within 10 minutes, cap 60 minutes). A tick that finds such a marker past its `retryAfter` proceeds as a normal attempt; success clears the marker, another failure re-escalates with the next backoff and attempt count. The log line for a skipped tick names the remaining wait. `commit-scoped` and `host-scoped` markers keep today's behaviour; marker identity checks and the process lock are unchanged.
2. `release-artifact-build-failed` whose detail is a transport failure of the source clone or fetch (`gnutls_handshake() failed`, `SSL_ERROR_SYSCALL`, `could not fetch … from promisor remote`, read timeout) is classified `retryable-transient`; a build failure whose detail is anything else (compile, test, missing dependency, unknown) stays `commit-scoped`. The classification is by an explicit detail allowlist in source, fail-closed.
3. `docs/runbooks/quiet-window-auto-deploy.md` documents the backoff, the log line and which failures still need `--clear-escalation`.

Out of scope: adding proxy environment to the launchd/systemd units; changing the five-attempt threshold; the artifact builder; the quiet-window blocker rules; the deploy-wait budget (landed 96f1a570).

Constraints: the marker file stays the single source of truth for escalation state; no new configuration surface; an `activationOutcomeProven: false` or malformed-target marker stays host-scoped; `scripts/deploy` tests cover all three scopes.

Acceptance: `npm run test:auto-deploy` (or the script's named test suite) green; tests show a capped retryable escalation proceeding after its backoff and clearing on success, re-escalating with a longer backoff on failure, an operator-action-required escalation staying stopped, a transport-detail build failure scheduling a retry and a non-transport build failure staying commit-scoped. Runbook updated in the same diff.

Route: implementation=senior-dev-astra-medium - the change alters deploy automation behaviour on production hosts; the failure (a stuck host or an unsafe self-retry of a non-transient failure) cannot be witnessed by the acceptance suite alone
