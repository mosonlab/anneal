API: Deleting a referenced Repo or Agent is refused with a typed 409

After this chain, `DELETE /repos/:repoId` and `DELETE /agents/:agentId` answer a typed 409 that names what still references the row instead of a bare 500 or an untyped message, and answer 404 for an unknown id (fixes #627).

Background: `DELETE /repos/:repoId` (`packages/api/src/routes/agents.ts`, near `app.delete("/repos/:repoId"`) is a bare `db.repo.delete()`. `Task.repo`, `Run.repo` and `TaskTemplate.webhookRepo` are `onDelete: Restrict` in `packages/db/prisma/schema.prisma`, so a Repo with any Task, Run or webhook-bound template history fails with Prisma P2003 and the route surfaces `500 {"error":"Internal server error"}`; an unknown id fails with P2025 and also answers 500. `DELETE /agents/:agentId` (same file, near `app.delete("/agents/:agentId"`) catches P2003 and answers `409 {"error":"Agent has task history; archive it instead"}` with no `code` and no statement of which kind of row blocks it; an unknown id still escapes as P2025 and answers 500. The Restrict edges to Agent are `Task.assigneeAgent`, `Run.agent`, `Session.agent`, `StaffingProfileEntry.assigneeAgent`, `StaffingProfileTier.agent` and `StaffingProfile.mergeTailRepairAgent`. These edges are deliberate for single-row deletes (see the comment above `StaffingProfileEntry` in the schema) and must stay: unlike the Project delete delivered in #626 (`packages/api/src/project-delete.ts`), a single Repo or Agent delete must not remove history. The archive route `POST /agents/:agentId/archive` already refuses with the typed code `agent_referenced_by_staffing_profiles` (`packages/api/src/staffing-profile-errors.ts`) and lists the profiles; the delete routes should refuse in the same typed style. Route refusals with a stable `code` and a `RefusalStatus` family are the repository convention (`packages/api/src/refusal-status.ts`).

Changes:
1. `DELETE /repos/:repoId` checks, inside one transaction with the delete, whether any Task, Run or TaskTemplate (`webhookRepoId`) still references the Repo. When at least one does, it answers `409` with a body of the shape `{ "error": <message>, "code": "repo_referenced", "references": { "tasks": <count>, "runs": <count>, "templates": <count> } }` where every count is the number of referencing rows for that kind (zero allowed). No row is deleted on refusal. When nothing references the Repo, the delete proceeds and answers `204`.
2. `DELETE /agents/:agentId` replaces its P2003 catch with the same pre-check pattern, answering `409` with `code: "agent_referenced"` and `references: { "tasks", "runs", "sessions", "staffingProfiles" }` where `staffingProfiles` counts distinct profiles that reference the Agent through an entry, a tier or `mergeTailRepairAgentId`. When nothing references the Agent, the delete proceeds and answers `204`.
3. Both routes answer `404 {"error":"Repo not found"}` / `404 {"error":"Agent not found"}` when no row has that id, and never answer 500 for a Restrict or missing-row condition.
4. The refusal codes are declared with their status family in a module under `packages/api/src/` following the `staffingProfileRefusalStatus` pattern (either extending an existing table or a new small table; do not inline string literals in the route).
5. `docs/operator-api.md` sections `DELETE /repos/:repoId` and `DELETE /agents/:agentId` document the 409 body shape, the 404 response, and state that the delete never cascades through history.
6. dbtests (in `packages/api/src/repo-route.dbtest.ts` for the Repo and a new or existing agent dbtest for the Agent, following their fixture conventions) cover: a Repo with one Task answers 409 with `references.tasks` equal to 1 and the Repo still exists; a Repo with no references answers 204 and is gone; an unknown Repo id answers 404; an Agent with one Run answers 409 with `references.runs` equal to 1 and the Agent still exists; an Agent named only by a staffing profile entry answers 409 with `references.staffingProfiles` equal to 1; an Agent with no references answers 204; an unknown Agent id answers 404.

Out of scope: any schema, migration or `onDelete` change; cascading or soft-deleting Repo or Agent history; changing `POST /agents/:agentId/archive` or its `agent_referenced_by_staffing_profiles` refusal; `DELETE /projects/:projectId` and `project-delete.ts`; the web console's delete confirmations and copy; any other route in `agents.ts`.

Constraints: The check and the delete run in one transaction so a reference created between them cannot slip through; a P2003 that still escapes (a reference kind this brief does not list) must surface as an error, not be swallowed into a 409. No raw SQL. Database tests are merge-gate evidence and are not run inside the Run.

Acceptance:
- `npm run typecheck -w @anneal/api`, `npm run lint -w @anneal/api` and `npm run test -w @anneal/api` are green.
- The merge gate's `test:db` is green and includes the seven dbtest cases in Change 6.
- `git diff origin/main -- packages/db/prisma` is empty.
- `git grep -n '"Agent has task history; archive it instead"' packages/api/src` returns nothing.
- `git grep -n "repo_referenced\|agent_referenced\b" packages/api/src docs/operator-api.md` shows the codes declared in one module, used by the two routes, and documented in both handbook sections.
